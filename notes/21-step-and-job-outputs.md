## What it is

**Outputs are values generated while a workflow runs and made available to other steps, jobs or reusable workflows.** One part of the workflow produces a value **once**, and other parts **consume** it.

Common examples:

```text
Build Number
Application Version
Commit SHA
Deployment URL
Security Scan Result
Release Version
```

Three types, which differ in **scope** (how far the value travels):

1. **Step outputs**: between **steps in the same job**. *Example:* a deployment URL, generated version, build metadata or API response from one step to the next. → **this topic**
2. **Job outputs**: from **one job to another**. *Example:* a deployment URL, release version, scan result or image tag from a build job to deploy, test or notify jobs. → **this topic**
3. **Reusable workflow outputs**: from a **reusable workflow back to its caller**. *Example:* deployment metadata from a central deployment workflow. → **[topic 22](22-reusable-workflows.md)**

> **Key observation:** the difference between the three is **scope**: step outputs inside a job, job outputs between jobs, reusable-workflow outputs between workflows. The idea is always the same: **one execution unit creates a value, another consumes it.**

> **Key observation:** **inputs bring data into** a workflow. **Outputs expose data generated by** a workflow. Together they're the main way information moves through a workflow.

---

## Why it exists

Workflows grow, and parts of them need to share information:

- a deployment step produces a **URL** that later steps must display
- a build job produces a **release version** that downstream jobs must deploy
- a reusable workflow produces **deployment metadata** that its caller needs afterwards
- a test job produces a **result** for a reporting job
- a security scan produces a **result** that a deployment job must evaluate

Without outputs you'd regenerate the same values, hard-code them, or invent hard-to-maintain workarounds.

```text
Deploy Application Job
         ↓
Creates Deployment URL

Send Notification Job
         ↓
Needs Deployment URL
```

The deploy job creates `https://cwvj-demo.com`. The notification job needs **exactly** that value. **How can one job share information with another?** With **outputs**. This improves **consistency, maintainability, reusability and traceability**, because every job uses the same information.

> **Terraform analogy:** Terraform **outputs** expose values like **public IPs, DNS names, load balancer endpoints or resource IDs** after creating infrastructure. GitHub Actions outputs work on the same principle, but mainly to pass values between **steps, jobs and workflows during a run**.
>
> Terraform outputs are often read directly by **users and tools**. GitHub Actions outputs are mainly for **workflow orchestration**, but their values can still reach humans or external systems: **shown in logs, put in deployment notifications, sent to external APIs, published to dashboards, or used by custom automation**.
>
> In practice they hold runtime information like **deployment URLs, release versions, image tags, scan results or infrastructure metadata**, shared within the workflow and sometimes with downstream operational processes.

> **Important:** outputs are for **values and metadata** (URLs, build numbers, versions, image tags, resource IDs, deployment results), **not files**. To move **files** between jobs, use **artifacts** (topic 24): binaries, container images, manifests, test reports, scan reports, coverage reports, logs, Helm charts and other deliverables.
>
> ```text
> Outputs   → Values and Metadata
> Artifacts → Files and Deliverables
> ```

**Jenkins comparison:** in Jenkins all stages usually share one workspace and Groovy variables (`def url = sh(script: '…', returnStdout: true)`). In GitHub Actions jobs run on **different machines**, so values must be **exported** explicitly as job outputs.

## Analogy

A **relay race**:

- **Step output** = passing a note to the **next runner on the same team, on the same track** (same job, same machine). They're right there, so you just hand it over (`steps.<id>.outputs`).
- **Job output** = the note has to go to a team **at another stadium** (another job on another runner). You must put it in the **official mailbox** (`jobs.<job>.outputs`), and they collect it from there (`needs.<job>.outputs`).
- **Artifact** = you need to send a **whole box of equipment**, not a note. That goes by courier (topic 24).

## How it works inside

```text
STEP OUTPUT
  step (id: deploy) runs:  echo "deployment_url=https://cwvj-demo.com" >> "$GITHUB_OUTPUT"
     │   $GITHUB_OUTPUT = path to a temp file the runner created just for this step
     ▼
  step ends → runner reads that file → stores {deployment_url: "https://…"} under steps.deploy.outputs
     ▼
  later steps in the SAME job: ${{ steps.deploy.outputs.deployment_url }} → substituted before they run

JOB OUTPUT
  job finishes → GitHub evaluates the job's outputs: map
       deployment_url: ${{ steps.deploy.outputs.deployment_url }}
     → stores job outputs in GitHub (control plane), not on the runner
     ▼
  dependent job (needs: deploy-job) starts on ANOTHER runner:
       ${{ needs.deploy-job.outputs.deployment_url }} → substituted from GitHub's stored value
```

🆕 Rules worth knowing:

- Outputs are always **strings** (use `fromJSON` to turn them into lists or numbers, topic 12).
- Limits: **1 MB per job**, **50 MB per workflow run** for all job outputs together.
- If an output **looks like it contains a secret**, GitHub **refuses to pass it** to other jobs and logs `Skip output 'x' since it may contain secret.`
- With a **matrix** (topic 26), every matrix job writes the same job output name, and **the last one to finish wins**.
- Only jobs listed in `needs` can read `needs.<job>.outputs`. That includes jobs further up the chain only if they're listed **directly**.

> ⚠️ **Deprecated syntax.** Old tutorials set outputs with `echo "::set-output name=deployment_url::https://…"` (and `::save-state::`). These were **deprecated in October 2022** because a malicious log line could fake them. ⚠️ *Corrected:* GitHub announced it would disable them, then **postponed the removal**; they still work but print a deprecation warning, and could be switched off at any time. (`set-env` and `add-path` are the ones that really are disabled.) **Always use `>> "$GITHUB_OUTPUT"`** (and `$GITHUB_STATE`). None of your original notes used the old syntax.

## Workflow YAML / commands

### Type 1: Step outputs

Step outputs let one **step** share information with another **step in the same job**.

```text
Generate Release Version Step
          ↓
Creates Version

Build Docker Image Step
          ↓
Needs Version
```

The first step generates `v1.0.1`. The second needs that exact value to build, tag or publish. Step outputs pass it without hard-coding or regenerating it.

```yaml
jobs:
  release-job:
    steps:
      - name: Generate Release Version
        id: version
        run: |
          echo "release_version=v1.0.1" >> $GITHUB_OUTPUT

      - name: Display Release Version
        run: |
          echo "${{ steps.version.outputs.release_version }}"
```

**Producing the output:**

- The step runs inside **`release-job`**. Step outputs are **scoped to the job**, so only later steps of that job can use them.
- **`id: version`** gives the step a unique identifier **within the job**. GitHub attaches the step's outputs to this ID, and other steps reference them through the **`steps`** context. **Without an `id`, no other step can reference its outputs.**

  > **Important:** any step that produces outputs should have an **`id`**, especially when **several steps in a job produce outputs**. The ID tells GitHub exactly **which step's** outputs you mean.

- `echo "release_version=v1.0.1" >> $GITHUB_OUTPUT` creates a value named **`release_version`** = **`v1.0.1`** and writes it to **`$GITHUB_OUTPUT`**.
- **`$GITHUB_OUTPUT`** is a special file GitHub provides for exposing step outputs. Anything written to it as **`key=value`** becomes a step output, read later with **`steps.<step-id>.outputs.<output-name>`**.

  > **`$GITHUB_ENV`** and **`$GITHUB_OUTPUT`** store **named entries**. Usually simple `key=value` lines, but **multi-line values** use the `<<EOF` syntax:
  >
  > ```bash
  > {
  >   echo "notes<<EOF"
  >   git log -3 --oneline
  >   echo "EOF"
  > } >> "$GITHUB_OUTPUT"
  > ```

- Output name → `release_version`. Output value → `v1.0.1`.

```text
Generate Release Version Step
           ↓
Creates Version
           ↓
Step Output
```

> **Important:** writing to `$GITHUB_OUTPUT` does **not** make the value available to all jobs. It's attached to the step that produced it. Steps run in order, so only **later steps** in the job can use it. A step **can't** read outputs of a step that hasn't run yet.

> **Connection to earlier topics:** `$GITHUB_OUTPUT` is like **`$GITHUB_ENV`** (used in topic 19). Both are GitHub-provided files that persist information during the run.
>
> - **`$GITHUB_ENV`** → creates **environment variables** for later steps in the same job (`$APPLICATION_VERSION`).
> - **`$GITHUB_OUTPUT`** → creates **outputs** read through expressions (`${{ steps.x.outputs.release_version }}`).
>
> ```bash
> echo "APPLICATION_VERSION=v1.0.1" >> $GITHUB_ENV    # environment variable
> echo "release_version=v1.0.1" >> $GITHUB_OUTPUT     # step output
> ```
>
> The syntax is similar but the purpose differs. (Topic 23 covers all environment files.)

**Consuming it:**

```yaml
- name: Display Release Version
  run: |
    echo "${{ steps.version.outputs.release_version }}"
```

- Both steps are in **`release-job`**, so the second can read the first's outputs through **`steps`**.
- `echo` just prints it. Real workflows use outputs to make deployment decisions, build file names or image tags, call APIs, and so on.

`${{ steps.version.outputs.release_version }}`:

- **`steps`** → the previously executed steps in this job
- **`version`** → the step's `id`
- **`outputs`** → the values it wrote to `$GITHUB_OUTPUT`
- **`release_version`** → the specific output

```text
Locating the Step
       ↓
Finding its Outputs
       ↓
Retrieving release_version
       ↓
Substituting the Actual Value
```

It resolves to `v1.0.1`, so the step actually runs `echo "v1.0.1"`.

> **Key observation:** step outputs are only for **later steps in the same job**. To cross a **job boundary**, use a **job output**.

```text
Generate Release Version Step
           ↓
Creates Version
           ↓
Step Output
           ↓
Display Release Version Step
           ↓
Consumes Version
```

> **Production insight / common uses:** generated versions, build metadata, commit info, API responses, scan results, dynamic resource IDs and release details shared between steps of one job.

### Type 2: Job outputs

Job outputs let one **job** share information with another **job**. That matters because jobs run on **independent runners** and **don't** share runtime information automatically.

```yaml
jobs:
  deploy-job:
    steps:
      - name: Deploy Application
        id: deploy
        run: |
          echo "deployment_url=https://cwvj-demo.com" >> $GITHUB_OUTPUT

    outputs:
      deployment_url: ${{ steps.deploy.outputs.deployment_url }}

  notify-job:
    needs:
      - deploy-job
    steps:
      - name: Send Notification
        run: |
          echo "${{ needs.deploy-job.outputs.deployment_url }}"
```

**The producing job (`deploy-job`):**

- The **Deploy Application** step (`id: deploy`) writes `deployment_url=https://cwvj-demo.com` to `$GITHUB_OUTPUT` as a **step output**. Without the `id`, GitHub couldn't know which step's outputs to expose.
- By default, step outputs stay **inside the job**. To make one available outside, **explicitly export it** as a **job output**:

  ```yaml
  outputs:
    deployment_url: ${{ steps.deploy.outputs.deployment_url }}
  ```

  The **`outputs`** block **maps** the `deploy` step's output to a job output named `deployment_url`. GitHub resolves the expression to `https://cwvj-demo.com` and assigns it. Downstream jobs then read it through **`needs`**.

> **Important:** step outputs need **no** `outputs:` block, because later steps see them through `steps`. Crossing a **job boundary** requires an explicit **job output**. Think of a job output as **a step output that has been intentionally exported** for downstream jobs.
>
> The step output name and job output name are the same here (`deployment_url`) for readability, but **they don't have to be**. The `outputs:` block is a **mapping layer**:
>
> ```yaml
> outputs:
>   application_endpoint: ${{ steps.deploy.outputs.deployment_url }}
> ```
>
> ```text
> deployment_url       → Step Output Name
> application_endpoint → Job Output Name
> ```
>
> Downstream jobs would read `${{ needs.deploy-job.outputs.application_endpoint }}`. This lets you expose names that make sense to consumers without renaming the step outputs.

```text
Deploy Step
      ↓
Creates Deployment URL
      ↓
Step Output
      ↓
Mapped to Job Output
      ↓
Available to Downstream Jobs
```

> **Key observation:** a **job output generates nothing itself**. It exposes values already produced by **steps in that job**. **Step outputs = communication within a job. Job outputs = communication between jobs**, via `needs.<job-id>.outputs.<output-name>`.

**The consuming job (`notify-job`):**

- **`needs: [deploy-job]`** makes it wait for `deploy-job` (jobs are parallel by default, topic 06) **and** gives access to its job outputs.
- `${{ needs.deploy-job.outputs.deployment_url }}`: **`needs`** = info from the jobs you depend on, **`deploy-job`** = the upstream job, **`outputs`** = its job outputs, **`deployment_url`** = the output. It resolves to `https://cwvj-demo.com`.

```text
Deploy Application Job
         ↓
Creates Deployment URL
         ↓
Exposes Job Output
         ↓
Send Notification Job
         ↓
Consumes Deployment URL
```

> **Common uses:** deployment URLs, release versions, scan results, build metadata, generated resource IDs, API-generated values and environment-specific deployment info between jobs.

> **Important:** job outputs are for **values**, not files, reports, binaries or logs. Use **artifacts** for those (topic 24).

> **Production insight:** typical job outputs are deployment URLs, release versions, scan results, infrastructure IDs, approval metadata and deployment status. (The capstone exports `image-tag` from the image-build job to the ECR push job.)

### Beyond URLs: what teams pass as outputs

The examples use a **deployment URL** because it's easy to picture, but production teams pass many kinds of runtime information:

- **Release version**: generated during the build, shared with packaging, publishing and deployment jobs, so every stage uses the **same version**.
- **Container image tag**: generated when the image is built, used by publishing, deployment or rollback, so every environment deploys **the exact image that was tested**.
- **Commit SHA**: shared across test, scan, package and deploy jobs, for **traceability** (every stage builds the same source revision).
- **Security scan results**: consumed by approval, reporting, notification or deployment jobs, often to **block deployments** on vulnerabilities, policy violations or compliance issues.
- **Artifact name or location**: so downstream jobs download, validate, publish or deploy the right build output.
- **Cloud resource information**: **load balancer DNS names, Kubernetes Ingress URLs, API Gateway endpoints, infrastructure IDs** created during provisioning, for deployment, testing, monitoring and notification jobs.
- **API-generated metadata**: **change request IDs, ticket numbers, deployment IDs, approval references, release IDs** from external systems, for **auditability, change management, governance** and enterprise processes.

The value itself matters less than **the scope at which it's consumed**. The same value can travel as a step, job or reusable-workflow output, depending on the design and where the consumers are.

> **Architectural note:** choose the output type by **how far the information must travel**. A deploy **step** shares a URL with later steps (step output). A deploy **job** exposes it to downstream jobs (job output). A central deploy **workflow** returns it to the caller (reusable-workflow output). What matters is **where the value is generated** and **who consumes it**.
>
> ```text
> Same Deployment URL
>          ↓
> Step → Step              → Step Output
> Job → Job                → Job Output
> Workflow → Workflow      → Reusable Workflow Output
> ```
>
> **Key observation:** outputs control **information flow across execution scopes**. Think less about the value and more about **the boundary it must cross**.

### Demo 1: share deployment information with step outputs

[`code/21-step-and-job-outputs/01-step-outputs-demo.yaml`](code/21-step-and-job-outputs/01-step-outputs-demo.yaml), saved as `.github/workflows/01-step-outputs-demo.yaml`:

```yaml
name: 01 - Step Outputs Demo

on:
  workflow_dispatch:

jobs:
  deployment-job:
    runs-on: ubuntu-latest
    steps:
      - name: Deploy Application
        id: deploy
        run: |
          echo "Deploying application..."
          sleep 3
          echo "deployment_url=https://cwvj-demo.com" >> $GITHUB_OUTPUT

      - name: Display Deployment Details
        run: |
          echo "Application deployed successfully."
          echo "Deployment URL:"
          echo "${{ steps.deploy.outputs.deployment_url }}"

      - name: Send Deployment Notification
        run: |
          echo "Sending notification..."
          echo "Application URL: ${{ steps.deploy.outputs.deployment_url }}"
          echo "Notification sent successfully."
```

- One job, three steps. The `deploy` step (simulated with `sleep 3`) writes `deployment_url` (name) = `https://cwvj-demo.com` (value) to `$GITHUB_OUTPUT` (the special file).
- Two **later** steps read it with `steps.deploy.outputs.deployment_url` (`steps` = earlier steps in this job, `deploy` = the ID, `outputs` = its values, `deployment_url` = the name).

> **Key observation:** step outputs work here because **all steps run in the same job context**.

### Demo 2: share deployment information with job outputs

[`code/21-step-and-job-outputs/02-job-outputs-demo.yaml`](code/21-step-and-job-outputs/02-job-outputs-demo.yaml):

```yaml
name: 02 - Job Outputs Demo

on:
  workflow_dispatch:

jobs:
  deploy-job:
    runs-on: ubuntu-latest
    steps:
      - name: Deploy Application
        id: deploy
        run: |
          echo "Deploying application..."
          sleep 3
          echo "deployment_url=https://cwvj-demo.com" >> $GITHUB_OUTPUT

    outputs:
      deployment_url: ${{ steps.deploy.outputs.deployment_url }}

  notification-job:
    runs-on: ubuntu-latest
    needs:
      - deploy-job
    steps:
      - name: Send Notification
        run: |
          echo "Sending notification..."
          echo "Application URL: ${{ needs.deploy-job.outputs.deployment_url }}"
          echo "Notification sent successfully."
```

- `deploy-job` writes a step output and **exports** it with `outputs:` (job outputs **generate nothing**, they expose values made inside the job).
- `notification-job` uses `needs: [deploy-job]` (order + access) and reads `needs.deploy-job.outputs.deployment_url` (`needs` = dependencies, `deploy-job` = upstream job, `outputs` = its job outputs, `deployment_url` = the name).

```bash
git add .
git commit -m "feat: add job outputs demo"
git push
```

**Execute:** **Actions → 02 - Job Outputs Demo → Run workflow**.

**Sample log output (notification-job):**

```text
Sending notification...
Application URL: https://cwvj-demo.com
Notification sent successfully.
```

In the workflow graph you'll see `deploy-job → notification-job`, two jobs on **two different runners**, with the URL crossing between them.

> **Key observation:** step outputs solve sharing **within a job**. Job outputs solve sharing **across jobs**. Next, [topic 22](22-reusable-workflows.md) lets reusable workflows return values to their caller.

## Where you'll use it

- **Image tag** from build → scan → push → deploy jobs (capstone `image-tag`).
- **Dynamic matrices:** a job outputs a JSON list, the next uses `fromJSON` (topics 12, 26).
- **Deployment URLs** → notification and smoke-test jobs.
- **Gating:** a scan job outputs `critical_count`, deploy runs `if: needs.scan.outputs.critical_count == '0'`.

## When it breaks

| Symptom | Meaning | Fix |
|---|---|---|
| Output is empty, no error | Missing `id`, wrong step ID or output name, or the step was skipped. | Check the `id` and names. Look at `${{ toJSON(steps) }}`. |
| `needs.x.outputs.y` empty | The job didn't declare `outputs:`, or the consumer doesn't list `x` in `needs`. | Add the mapping. Add `needs: x`. |
| `Skip output 'y' since it may contain secret.` | The value contains (or looks like) a secret. | Don't pass secrets as outputs. Pass the secret again in the next job. |
| `Unable to process file command 'output' successfully. Invalid format` | A multi-line value written as `key=value`. | Use the `<<EOF` delimiter syntax. |
| Warning about `set-output` / it doesn't work | Deprecated command. | Use `>> "$GITHUB_OUTPUT"`. |
| Matrix job output has the "wrong" value | The last matrix leg to finish overwrote it. | Use per-leg names, or artifacts. |

## Quick recap

- **Step output:** `echo "k=v" >> "$GITHUB_OUTPUT"` in a step with an `id` → `steps.<id>.outputs.k`, same job only.
- **Job output:** map it in `jobs.<job>.outputs` → `needs.<job>.outputs.k` in jobs that `need` it.
- Outputs are **strings**, limited in size, secret-filtered, and **values not files**.
- `::set-output` is **deprecated** (still works with a warning; removal postponed). Use `$GITHUB_OUTPUT`.
- Choose the output type by **which boundary the value crosses**.

**Interview questions**

1. **Q: How do you pass a value from job A to job B?**
   A: In A, write it to `$GITHUB_OUTPUT` in a step with an `id`, map it under `jobs.A.outputs`. In B, set `needs: A` and read `${{ needs.A.outputs.name }}`.
2. **Q: Why was `::set-output` deprecated?**
   A: It was parsed from log output, so untrusted text printed in a log could inject or override outputs. The file-based `$GITHUB_OUTPUT` is safer.
3. **Q: Outputs or artifacts for a test report?**
   A: Artifacts. Outputs are for small string values and metadata.
